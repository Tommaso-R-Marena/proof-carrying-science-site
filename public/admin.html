Marketplace publication

Only publish work PCS genuinely needs.

The marketplace is default-deny. Draft, paused, satisfied, or retired work is not publicly startable—even by direct API ID. Publication changes are Founder/Owner-only and audit-logged.

RuleA useful idea is not automatically a public task. Publish only when PCS has a concrete need, finish line, verification rule, and capacity to review the output.

Creation never publishes automatically.

Dependency graph editor

Make prerequisites explicit enough to audit.

Edges say what accepted artifact flows downstream; gate groups define ALL / ANY / AT_LEAST(k) unlock logic. Hard-edge cycles are rejected server-side and every graph change is audit-logged.

Design ruleUse a hard dependency only when downstream work is genuinely unsafe or meaningless without the accepted upstream output. Use informative edges for useful context that should not block parallel work.

PCS Arena validation

Validate the science before validating the score.

Leaderboard placement is challenge-local. Review the artifact, correct any claimed structure counts, and only then verify or reject the entry. Arena results never automatically change contributor level or skill authority.

Proof Quest adult opt-in research dataset

Only the Founder/Owner may inspect a deidentified training-research export. Entries contain synthetic puzzle step orders, scores, hints and puzzle versions; they are not Lean proofs. Account IDs and emails are excluded from the export. Contributors may erase their stored attempts.

Ongoing roles

Review recurring responsibility separately from bounded work.

Operations, communications, and outreach roles do not raise technical authority and do not reserve research tasks.

Pending task applications

Approve the person, not merely the level.

Level + verified skill + founder decision. A pending application never reserves the task.

Reservation checkpoints

Keep active work moving or release it.

A concrete checkpoint can earn a bounded extension. Silent reservations release automatically.

Competency verification

Auto-score the screen; keep authority manual.

Contributors can use a fresh variable evaluation or submit evidence/application directly. A passing auto-score is only screening evidence. You still make the final skill/task approval manually, with a target response within 1 business day and no later than 2.

Submission triage

Inspect → run CI → request fixes or accept → integrate.

For GitHub-backed tasks, submission files are staged to isolated branches. Only a successful check on the exact PR head permits acceptance, and only the Founder/Owner can merge. A passing CI result never proves scientific truth.

Decision guide: Check the artifact and claimed scope, inspect GitHub results, request improvements when necessary, and document the independent review rationale. Marketing/outreach evidence is classified as activity or independently supported outcome; neither rewards unsolicited spam.
Production source integration

Promote checked contributions into PCS production

Separate from accepting an archive contribution. The Owner must map each reviewed original file to a narrowly permitted production path. A fresh Lean/PCS or website CI run on the exact promotion PR is required, followed by explicit approval and a final merge check.

Production gate: accepted archived source → exact-byte mapping → isolated production PR → fresh runnable tests → Owner approval on a specific commit → Owner squash merge. Missing CI (including quota exhaustion) blocks approval and merging. No 'force pass' control exists.

Contributor + governance authority

Immutable audit archive

Append-only, hash-chained operational history.

Application/database rules reject updates and deletions to this archive. Each event commits to the previous event hash. Infrastructure owners could still destroy the underlying database itself, so this is tamper-evident and application-immutable—not physically indestructible.
