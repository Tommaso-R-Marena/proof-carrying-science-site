One command to produce. One command to verify.

Guided intake before attestation

The scientist no longer starts by writing PCS JSON.

Use the local Project Mapper or pcs discover-v06 to inventory an existing project and draft only the supported, high-confidence checks PCS can currently understand. The draft is deliberately non-attestable until human confirmation re-hashes the selected files.

Step 0Discover
pcs discover-v06 ./my-project

Locally inventories regular files, excludes key material, snapshots SHA-256/size, recommends supported scientific checks, and statically maps high-confidence Python/Jupyter artifact dependencies without executing user code.

Human gateConfirm
pcs confirm-v06 ./my-project/pcs-manifest.draft.json

Re-hashes every selected artifact, records explicit confirmation, and produces manifest.json. If files drift afterward, attestation rejects them.

The complete loop

From a bounded workflow to a portable assurance package.

The producer never gets to declare itself accepted. PCS separates scientific replay, package validity, signer authenticity, and the receiving organization's acceptance policy.

ProducerBuild and attest
pcs attest-v06 project/manifest.json -o study.pcs.zip --private-key organization-private.pem --public-key organization-public.pem

Copies exact artifacts into the package first, replays supported checks against those copied bytes, builds the typed v0.6 certificate and normalized decision set, signs the package, verifies the candidate ZIP, then atomically publishes it.

ReviewerVerify + apply policy
pcs verify-v06-bundle study.pcs.zip --public-key trusted-public.pem --expected-signer-fingerprint <fingerprint> --policy reviewer-policy.json --receipt receipt.json --reviewer-private-key reviewer-private.pem --receipt-signature receipt.sig.json

Reads the ZIP without extracting it, verifies the signer and exact file set, reruns supported scientific checks, regenerates normalized decisions, applies the reviewer's acceptance criteria, then optionally signs the exact receipt bytes with a separate reviewer identity.

Independent environment provenance

A lockfile is evidence only if the reviewer can regenerate the same environment contract.

Guided discovery captures Python/R dependencies, lockfiles, interpreter constraints, Conda/Nix specifications, and Docker/OCI base references without executing package managers or builds. After package binding, the reviewer reconstructs those exact environment files and regenerates the canonical environment contract before workflow or scientific replay.

Pinned

Strength is explicit

PCS distinguishes loose declarations, application lockfiles, hash-pinned requirements, digest-pinned containers, and stronger combined states instead of calling all of them “reproducible.”

Replay

Freshly re-derived

The signed pcs-environment-capture-v1 proposition must equal a fresh capture over the exact delivered environment source bytes.

No exec

Verification stays non-executing

PCS can emit pcs-environment-plan.json and a review-before-run reconstruction script, but verification never runs installers, package managers, or container builds automatically.

Inspect reconstruction plan

pcs environment-plan-v06 manifest.json -o environment-plan.json --script reconstruct-environment.sh

The generated script may invoke package managers or container builds and must be reviewed before execution. It is never executed by verify-v06 or verify-v06-bundle.

Prepare a verified replay workspace

pcs prepare-environment-v06 study.pcs.zip -o replay-workspace --public-key trusted-public.pem --expected-signer-fingerprint <fingerprint>

PCS fully verifies the delivered bundle first, then materializes the exact signed project-relative artifact tree plus pcs-environment-workspace.json, the replay plan, and a review-before-run reconstruction script. Materialization is non-executing and is published atomically only after preparation succeeds.

Independent workflow provenance

Signed workflow is not trusted just because it is signed.

After package hashes and producer signatures pass, the reviewer reconstructs project-relative source files from the exact delivered artifacts and reruns static workflow discovery. A forged dependency edge therefore fails before ordinary scientific evidence replay, even if the producer recomputed hashes and re-signed the package.

Exact

Clean AST graph

For clean Python/Jupyter analysis, the complete signed input/output set must equal the freshly rediscovered set.

Subset

Partial / R / browser graph

Every signed edge must be rediscovered, while PCS explicitly does not claim the set is complete.

Fail

Mismatch stops verification

The dedicated workflow_replay stage fails before claim replay or normalized-decision regeneration.

Why policy is separate

Valid does not mean accepted.

A PCS package can be perfectly authentic and replay-consistent while honestly carrying a failed or open scientific claim. The receiving organization decides whether those claim statuses are acceptable for its use case.

PCS validityDid the delivered bytes, signatures, replay results, and normalized decisions agree?
Reviewer acceptanceDo the verified claim statuses and signer identity satisfy this reviewer's external policy?

Example policy

The producer does not embed or sign the reviewer's acceptance criteria. The reviewer supplies them at verification time.

Independent review provenance

Producer signs the package. Reviewer signs the receipt.

The two signatures serve different purposes. The producer signature authenticates the scientific delivery. After independent verification and policy evaluation, the reviewer may sign the exact receipt bytes with a separate Ed25519 key.

Producer identityBinds certificate + exact package manifest.
Reviewer identityBinds exact receipt SHA-256, bundle SHA-256, policy SHA-256, certificate/index commitments, PCS validity, and reviewer acceptance.

Verify the review record later

pcs verify-receipt-v06 receipt.json --signature receipt.sig.json --reviewer-public-key reviewer-public.pem --expected-reviewer-fingerprint <reviewer-fingerprint>

A reviewer signature attests to the review record. It does not elevate claim assurance, repair failed science, or replace PCS package verification. Reviewer private keys should stay local; this website never requests them.

Multi-reviewer quorum

Require multiple independent approvals without merging reviewer authority.

PCS can aggregate separately signed review receipts under a role-aware quorum policy. A 2-of-3 rule can require at least one computational reviewer and one domain reviewer while allowing a statistical reviewer to dissent without changing the underlying PCS verdict.

Computational

Accepted

Valid signed receipt, authorized fingerprint, and the computational-review policy SHA-256 required by the quorum policy.

Domain

Accepted

Independently verified the same exact bundle/certificate/index subject under its own domain-review policy.

Statistical

Dissent allowed

A non-accepting or unavailable third reviewer does not count, but cannot rewrite the other reviewers' receipts or the PCS scientific record.

Total threshold2 of 3
Required roles1 computational + 1 domain
Cross-bundle mixingRejected
Duplicate identityCannot count twice

Verify the quorum

pcs verify-quorum-v06 --quorum-policy review-quorum-policy.json --review-set review-set.json -o quorum-result.json

The quorum engine groups accepted signed reviews by exact bundle SHA-256, certificate semantic/integrity hashes, and normalized-index semantic hash. Reviews from different studies can never be combined to satisfy the threshold.

Adaptive replay scheduling

Learn where failures tend to surface without learning the verdict.

PCS now includes deterministic scheduling baselines and a contextual LinUCB-style bandit. The optimization target is time to first detected failure. Every mandatory check still runs, and the scheduler is explicitly excluded from claim assessment, normalized decisions, reviewer policy, signed receipts, and quorum approval.

Shadow first

Observe before acting

--shadow-bandit records what the learned scheduler would choose while PCS continues to execute the configured deterministic order.

20 + 3/type

Cold-start guard

Active bandit ordering requires at least 20 eligible historical observations overall and 3 for every check type in the current package. Otherwise PCS falls back to failure-per-second.

Invariant

All checks still run

Execution order may change. Scientific evidence scope, check semantics, claim status, reviewer policy, and quorum semantics may not.

Boundary

External evidence stays explicit

Formal, empirical, statistical, and provenance evidence is not auto-promoted to PASS by the MVP producer.

Formal boundary

The executable MVP and the formal theorem stack are related, but not identical.

The current v0.6/v2 executable format and the machine-checked frontier stack target the same certificate/package/normalized-decision representation. On the canonical STORED-archive path, Lean now decodes raw ZIP bytes itself, proves SHA-256 equal to an independent FIPS 180-4 specification, and independently replays all five built-in predicates. The PK/PD reference checker additionally has a proved real-valued analytic meaning. Authoritative production validity still requires the compiled Lean authority. The remaining boundary is narrower: Ed25519 unforgeability and RFC 8032/SHA-512 correspondence, workflow-front-end analysis, environment meaning beyond EnvFacts, external validators, legacy non-canonical ZIPs, and operational invocation/runtime components.

Executed reproducibility evidence

The signed environment is now reconstructed and replayed, not merely described.

PCS keeps ordinary verification and execution separate: prepare-environment-v06 verifies and materializes the signed workspace, while execute-environment-v06 explicitly launches the sandboxed replay. The completed evidence campaigns exercise the actual execution path.

Cross-machine OCI

PASS

One signed campaign replayed on Ubuntu 24.04 amd64, Ubuntu 24.04 ARM64, and Ubuntu 26.04 amd64, while also varying Debian container bases, lock state, and image provenance.

Docker ↔ Podman + native R

PASS

The same signed computation reproduced under Docker and real rootful Podman. A separate R-native workflow passed on Docker amd64, Docker ARM64, and rootful Podman amd64. Rootless Podman container execution on the managed CI host remains unestablished.

Offline restoration + ABI

PASS

PCS restored NumPy from signed hash-locked architecture-specific wheels and restored an R environment from a signed local repository through renv::restore(), all with build networking disabled. Native-extension hashes differed by architecture while scientific outputs remained byte-identical.
