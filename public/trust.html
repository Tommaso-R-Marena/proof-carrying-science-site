Guided discovery boundary

Human confirmation required

discover-v06 and the local Project Mapper are recommendation layers. They inventory files, propose supported checks, and may statically infer Python/Jupyter artifact dependencies without executing user code. The generated manifest carries pcs_intake.status = "draft" and cannot enter attestation.

Explicit confirmationconfirm-v06 re-hashes every selected artifact. attest-v06 checks the same snapshot again, so onboarding automation cannot silently authorize its own claims or sign changed bytes.

Independent environment replay boundary

Implemented

Dependency files, lockfiles, interpreter constraints, and container specifications are not trusted merely because the producer signed them. After exact package binding, PCS reconstructs the delivered environment source tree and regenerates the canonical environment capture before workflow or scientific replay.

Strength labelsPCS distinguishes strongly_pinned, container_base_pinned, locked_application_dependencies, hash_pinned_dependencies, declared_dependencies, and environment_unspecified. These are descriptive reproducibility states, not proofs of runtime equivalence.
Authoritative handoffThe browser Project Mapper previews environment structure only. confirm-v06 regenerates the canonical Python environment capture from the exact reviewed artifact bytes before marking it confirmed.
Explicit execution boundaryOrdinary reviewer verification does not run package managers, dependency installers, container builds, or user installation hooks. After verification, prepare-environment-v06 materializes an inert signed workspace; the separate explicit execute-environment-v06 command performs sandboxed OCI reconstruction and replay.
Verified replay workspaceprepare-environment-v06 first performs full bundle verification, then atomically materializes the exact signed project-relative artifact tree plus workspace metadata, replay plan, and reconstruction script. Execution remains a separate explicit action through execute-environment-v06.
Adversarial boundaryA forged environment dependency or interpreter claim remains expected to fail at environment_replay even if the producer recomputes certificate/package hashes and signatures.

Independent static-workflow replay boundary

Implemented

Human confirmation and producer signature are not sufficient to establish a static dependency claim. After exact package binding, the v0.6 verifier reconstructs the delivered source tree and reruns static workflow analysis before scientific evidence replay.

Exact modeClean Python/Jupyter AST mappings require exact equality between signed and freshly rediscovered input/output sets.
Subset modePartial, R, browser-heuristic, or ambiguity-reduced mappings require every signed edge to be rediscovered but do not claim completeness.
Validation statusThe full hosted integration suite and mainline product/formal gates have executed the current workflow-replay regressions successfully.

Reviewer-signed receipt boundary

Implemented

The producer and reviewer can use different Ed25519 identities. After PCS verification and reviewer-policy evaluation, the reviewer may sign the exact receipt file. A later auditor can verify that signature without rerunning PCS.

What is signedExact receipt SHA-256 plus bundle SHA-256, policy SHA-256, certificate semantic/integrity commitments, normalized-index commitment, PCS validity, and reviewer acceptance.
What it does not meanA reviewer signature proves authorship of the review record under the selected key. It does not make the scientific model empirically adequate or elevate the assurance class.

Multi-reviewer quorum boundary

Implemented

PCS can aggregate independently signed reviewer receipts under a separate quorum policy. The quorum layer never changes the PCS scientific verdict; it decides whether enough authorized independent reviewers accepted the same exact reviewed subject.

What countsValid reviewer signature, pcs_valid: true, reviewer_accepted: true, authorized reviewer fingerprint, role-specific required policy SHA-256, and exact bundle/certificate/index subject match.
Anti-combination rulesReviews from different scientific bundles are grouped separately and cannot be pooled. Duplicate reviewer identities are disqualified so one signing key cannot occupy multiple seats.
Direct runtime check2-of-3 computational+domain quorum passed; cross-bundle mixing, duplicate identity, and wrong role-policy hash were each rejected in a standalone cryptographic scenario.

Adaptive replay scheduler boundary

Experimental

PCS v0.6 implements deterministic replay-order baselines plus a contextual LinUCB-style bandit. The scheduler may prioritize which mandatory check runs first, but it is not consulted by scientific check semantics, claim assessment, normalized decisions, reviewer policy, signed receipts, or quorum approval.

Cold-start guardActive bandit ordering requires at least 20 eligible observations overall and at least 3 observations for every check type in the current package. Sparse history falls back to deterministic failure-per-second ordering.
Telemetry boundaryPersisted telemetry contains check type, size/count context, outcome/failure class, wall/CPU timing, and SHA-256-derived evidence IDs. Artifact contents are not written into scheduler history.
Evidence statusA synthetic direct runtime exercise preserved all mandatory checks and produced an 11× counterfactual time-to-first-failure estimate. Production-workload speedup has not yet been established.

Explicit non-claims

What PCS does not currently certify.

The strongest trust posture is one that names its limits. The following remain separate from the current machine-checked result.

01

Scientific truth

Formal soundness of a decision rule does not prove that a biological, chemical, or clinical model is empirically adequate.

02

Production correspondence + external contracts

The v0.6/v2 theorem chain is machine-checked, but Python acceptance is not yet proved to refine Lean. ZIP decoding, environment capture, and replay fidelity for non-chemistry checks remain explicit contracts.

03

Regulatory status

PCS does not currently claim FDA certification, GxP validation, clinical validity, safety, efficacy, or regulatory acceptance.

04

Arbitrary code correctness

The current product supports bounded predicates and adapters; it does not prove arbitrary Python, R, C++, notebooks, solvers, or simulations correct.

05

Cryptographic standard boundary

Lean implementations and wiring exist, but SHA-256 and Ed25519 are still validated against standards by known-answer vectors rather than independent specification-equivalence proofs; Ed25519 unforgeability remains a cryptographic assumption.

06

Reviewer judgment

PCS can enforce an explicit acceptance policy, but the receiving scientist or organization remains responsible for deciding which evidence and assurance classes are sufficient.

Claim semantics boundary

Natural language explains the claim. The typed predicate defines it.

PCS does not treat arbitrary prose as executable scientific logic. Human intent is matched only to a supported claim template; that template supplies typed fields, an exact predicate, and a matching check specification. The verifier evaluates that structured object, not the prose label.

1

Intent

A scientist can describe the goal in ordinary language. PCS may use those words to suggest a supported template, but the text itself carries no formal authority.

2

Typed predicate

The user confirms concrete fields such as artifact IDs, identity keys, units, reaction coefficients, model/output bindings, or numeric tolerances.

3

Exact verification

The built-in check deterministically implies the predicate recorded in the certificate. Unsupported statements remain explicitly unformalized instead of being guessed.

Current supported formal claim familiescsv_disjoint, reaction_balance, unit_compatible, pkpd_contract, and pkpd_reference_match.
