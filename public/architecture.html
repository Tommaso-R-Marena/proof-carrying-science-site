Technical architecture

A small acceptance path around a large scientific workflow.

PCS is designed around a simple trust principle: the system that produces a scientific result does not get to define whether its own evidence is sufficient. Producers emit artifacts and claims; a separate verification path replays supported checks, binds evidence, authenticates delivery, and applies reviewer-controlled policy.

Usability layer

Guided project mapper, outside the scientific verdict boundary.

Discover

Local artifact + workflow mapping

Inventory files, hash bytes, inspect bounded JSON/CSV structure, and statically infer conservative Python/Jupyter file dependencies without executing source code.

Confirm

Explicit human gate

A discovery draft cannot be attested. Confirmation re-hashes the exact selected artifact snapshot.

Attest

Drift protection

Attestation checks the confirmed snapshot again before copying bytes into the signed package.

v0.6 delivery invariants

The serialized artifact is part of the verification target.

JCS

Canonical bytes

Certificate, signatures, package manifest, normalized wires, and index use the frozen v0.6 JCS profile with strict UTF-8 and duplicate-key rejection.

ZIP

Deterministic delivery

Sorted ZIP_STORED members, fixed metadata, exact manifest-signed file set, post-build self-verification, and atomic publication.

Policy

Receiver-owned acceptance

Policy is supplied by the reviewer, not embedded by the producer. The receipt binds its exact bytes by SHA-256.

Benchmark + adaptive scheduling

Learn where failures occur without learning the verdict.

The benchmark-v06 registry pins public-data fixtures and expected outcomes. Separately, the v0.6 replay path now implements deterministic scheduling baselines plus a contextual LinUCB-style bandit trained from observational replay telemetry. Its only authority is check order: all mandatory evidence still runs and scientific verdicts remain deterministic.

Deterministic

Benchmark verdicts

PASS/FAIL remains a pure function of exact fixture bytes, checker semantics, and explicit expectations.

LinUCB

Implemented scheduling only

The learned component can rank mandatory checks by an upper-confidence estimate of failure probability per millisecond. Shadow mode and cold-start fallback prevent sparse history from silently controlling execution.

Guarded

Promotion requires evidence

Bandit ordering requires ≥20 historical observations overall and ≥3 for every current check type. Production speedup remains unclaimed until real workflow telemetry supports it.

Audit architecture

Three distinct trust decisions.

1

Producer authenticity

Who issued the scientific package? Bound by the producer Ed25519 signature.

2

PCS verification + policy

Did the package replay correctly, and did it satisfy this reviewer's explicit acceptance criteria?

3

Reviewer provenance

Who performed and attested to that exact review? Bound by a separate reviewer-signed receipt.

Multi-party review governance

Approval can require independent roles without allowing signatures to bleed across studies.

2-of-3

Total threshold

Organizations can require a minimum number of accepted signed review receipts.

Roles

Role thresholds

For example, at least one computational reviewer and one domain reviewer, each pinned to a distinct required policy hash.

Subject

Exact review target

Quorum is evaluated per exact bundle/certificate/index commitment tuple. Reviews over different scientific deliveries are never pooled.

Trust statement

Formal verification does not certify biology.

The current PCS v0.6/v2 package/archive assurance theorems are machine-checked under Lean 4.28.0. They connect accepted canonical package structure and normalized decisions to scoped scientific assurance under explicit external contracts; reaction_balance replay faithfulness is proved internally. The deployed v0.6 path requires compiled Lean acceptance for authoritative validity. This still does not prove that an underlying scientific model is empirically adequate for the world, nor does it erase the ZIP-decoder/materialization, capture, replay, process-invocation, or cryptographic boundaries.

Correctness

Did the computation follow its declared rules?

Formal proof and executable replay can address this dimension within a bounded model.

Adequacy

Is the model scientifically appropriate?

This requires empirical/statistical evidence and domain judgment; formal proof alone cannot supply it.

Acceptance

Is the evidence enough for this reviewer?

That is an external policy decision, not something the producer should silently choose.

Claim semantics boundary

Natural language explains the claim. The typed predicate defines it.

PCS does not treat arbitrary prose as executable scientific logic. Human intent is matched only to a supported claim template; that template supplies typed fields, an exact predicate, and a matching check specification. The verifier evaluates that structured object, not the prose label.

1

Intent

A scientist can describe the goal in ordinary language. PCS may use those words to suggest a supported template, but the text itself carries no formal authority.

2

Typed predicate

The user confirms concrete fields such as artifact IDs, identity keys, units, reaction coefficients, model/output bindings, or numeric tolerances.

3

Exact verification

The built-in check deterministically implies the predicate recorded in the certificate. Unsupported statements remain explicitly unformalized instead of being guessed.

Current supported formal claim familiescsv_disjoint, reaction_balance, unit_compatible, pkpd_contract, and pkpd_reference_match.
