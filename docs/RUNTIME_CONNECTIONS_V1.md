# Connected website runtime, 2026-11-03

The website now connects an actual browser model proposal to an exact mathematical
claim and a separately executed Lean proof. The scientific example can also be
checked against its original CSV bytes in the native app. Proof games can save
the receipt of their actual fresh check rather than always downloading an older
catalog proof.

This is integration work, not a new AI-safety theorem or evidence of improved
proof-search accuracy. No production PCS authority, Lean specification, trained
weights, selected checkpoint or automatic-training policy changed.

## What executes

| User action | Actual executor | Scope |
| --- | --- | --- |
| Ask the walkthrough to repair a rule | Pinned 384-weight JavaScript ranker, followed by a separate exhaustive finite evaluator | Registered fictional worlds with one to three individuals |
| Check that exact repair on the public site | Workbench, existing consented public job, frozen proof-search family and Lean 4.28 | Explicitly displayed unary-predicate interpretation on natural numbers |
| Check that repair in the connected local runtime | Actual frozen verified-memory model, typed proof actions and Lean 4.28 | Same exact interpretation, without public submission |
| Move a Bridge Builder or Memory Workshop card | Source-bound recorded Lean state graph | Catalog replay; no kernel executes just because a card moves |
| Run the game's fresh check | Local session/step API or consented public job | Exact theorem, route, library and approved kernel assumptions |
| Compare the scientific CSV example on the website | JavaScript parser and preservation checker | Browser calculation, not a fresh Lean verdict |
| Review the same original CSVs in a newly built native app | Source-bound native Lean CSV executable, automatically invoked for that review | Original bytes, selected policy and comparison digest |
| Open an evidence viewer or information page | Relevant parser, recorded report, or navigation | Viewing a record does not rerun its experiment |

[runtime-connections.json](../public/runtime-connections.json) explicitly classifies
all 75 pages and their entrypoint modules. `check_runtime_connections.mjs` checks
page coverage, entrypoints, literal module dependencies, capability links and
the approved core/model inventory. This is a structural audit, not execution
attestation. The capability catalog exposes 22 paths; the source inventory still
contains 41 core checkpoints, four core families and five browser weight files.
Comparison checkpoints are not silently promoted into hosted model choices.

## Model proposal to proof

1. The browser verifies the ranker's numerical weights against digest
   `1202f553597d3e946a99f38131656ee06a0ed2937ef2da2ae9aea93df33af4ee`.
2. The handoff receiver reruns the model and all finite checks, selects its exact
   accepted edit, and reconstructs a closed typed mathematical interpretation.
3. On the public site, the workbench previews that interpretation. Meaning and
   publication consent start unchecked. Opening the handoff submits nothing.
4. The proof receipt must match that interpretation. Combined evidence preserves
   the proposal, model identity, goal, actual proof actions and kernel audit.
5. An independent receiver reconstructs the commands from typed actions and
   reruns Lean. It never executes producer-supplied Lean source.

The finite model and the natural-number interpretation have different domains.
The separate Lean proof is not inferred from finite success. These demonstrations
repair elementary identity statements, not deployed assistant behavior. A symbolic
portfolio winner is attributed to the symbolic component, not the learned model.

## Run the connected local website

Use the exact core checkout
`f20f3cab2938f2e085f137185e88f4700d5da2ed`, its hash-locked CPU dependencies,
and Lean 4.28.0. From a clean committed website checkout:

```sh
python scripts/serve_connected_site.py --core /path/to/proof-carrying-science
```

Open `http://127.0.0.1:8769/model-walkthrough.html`, run either example, then
choose **Run local Lean on this exact repair**. The same origin serves the full
Lean lab and both proof games with real local session/step checks. The gateway
checks all model/source inventory pins before launching its own backend, serves
only captured frontend bytes, and rejects changed assets, foreign origins,
unreviewed routes and oversized requests. Source changes require a restart.
`--development` explicitly allows an uncommitted frontend snapshot.

Public proof jobs are disabled by default. `--allow-public-jobs` enables only the
fixed existing public service; its usual publication consent and quota still
apply. The gateway provides no account, donation or deletion backend. Those
operations remain on the public website. A failed local proof service cannot
silently become a public request or a recorded positive answer.

The gateway is a convenience for a trusted local host, not a sandbox, immutable
root, credential enclave or independently attested model runner. The backend's
loopback port is reachable by other processes on that host. Its Python, toolchain,
operating system and receiver checkout remain trust dependencies. POSIX startup
and cleanup are exercised here; Windows process-tree cleanup is implemented but
has not been independently qualified by the gateway campaign. Portable checker
platform builds are a separate existing qualification.

```sh
node scripts/check_runtime_connections.mjs

python scripts/test_model_lean_replay.py --core /path/to/exact/core
```

The independent receiver captures the evidence once, checks its own reviewed
JavaScript/Python source profile, reproduces the proposal, verifies the core,
library and checkpoint bytes, reconstructs the typed proof, compares the proof
and axiom audit, and checks sources again. Matching checksums do not authenticate
a sender. A negative control changes producer proof text and recomputes its
checksums: the regenerated Lean proof must still expose that alteration.

Route tests reject cross-request receipts, altered source/action digests,
unapproved axioms, changed libraries, failed results and stale inputs. The UI
invalidates fresh evidence whenever a route changes, including undo and restart,
and captures asynchronous inputs before hashing. One in-flight local check is
allowed per route. Pending public jobs use the existing idempotency/recovery
journal. Local-only receipts disclose that the legacy backend does not
independently attest its source revision; the recommended gateway checks source
before launch, but cannot create a hardware attestation.

## Evidence and limits

Raw actual public-job-entrypoint outputs and combined replay files live under
[evidence/runtime-wiring-v1](evidence/runtime-wiring-v1). Those locally executed
public-job entrypoints are labeled **recorded examples**, not fabricated GitHub
runs. The two hybrid checks were verified by `ordinary_Std` using `propext`.
The actual selected verified-memory checkpoint
`869732df6ef29bac30c9878b57e5d8c7e0f1fba41231d0d10c5f1112309aee57`
proved the implication repair in six expansions with an empty axiom list.
The real browser-to-local-runtime campaign reproduced both ranker suggestions,
used this checkpoint for six and five search expansions respectively, and
returned empty axiom lists for both exact interpretations. It exported the
matching evidence, reimported it as recorded evidence, and refused altered goals.
Independent replay verifies mathematical proof, not the physical occurrence of
neural generation. Existing negative prospective model comparisons remain valid.

Automated browser campaigns, native checks and protected CI exercise actual
engines. Separate failure fixtures are not real authorization evidence. No human
participants, comprehension result, scientific acceptance, universal AI-safety
guarantee or learned advantage is established by these integrations. Formal truth,
implementation correspondence, scientific assumptions and empirical validity
remain separate.
