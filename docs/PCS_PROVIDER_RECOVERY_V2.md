# Provider readiness and definite no-dispatch recovery v2

The Lean job service now checks whether the approved public GitHub checker can run **before charging a proof admission**. An unavailable token/transport, a private repository, a different default branch or main revision, a missing/disabled workflow, and oversized or malformed metadata stop before creating a new journal or spending the 2/IP/24-hour and 12/global/day proof admissions. The existing 120/hour per-client retry protection remains in the Worker. A separate fixed internal global scope permits at most 240 initial/created readiness attempts per existing 60-minute rate-limit window, regardless of client IP. Acknowledged ticket reuse bypasses this metadata allowance. Both guards run before metadata reads; rejected attempts consume no proof admission. The saved browser idempotency key remains usable after readiness recovers.

`preflightDispatch(env, transport)` performs three fixed authenticated metadata GETs: repository, `/git/ref/heads/main` and the exact `pcs-lean-public.yml` workflow. Each fetch has a six-second AbortSignal deadline and a 32 KiB response bound. It returns `pcs-lean-provider-readiness-v1` with false PCS authority. Failures expose only fixed diagnostic codes, never provider bodies, credentials, statements or arbitrary exception text. This is a point-in-time observation, not a reservation or a proof. `/api/lean-research/status` continues to report configuration only.

After the single journal CAS winner consumes admission, `dispatch` repeats readiness immediately before the POST. Local statement/binding validation and ticket signing also occur before the external effect. A subsequent readiness failure is a terminal journal `failed/provider_unavailable`, with `dispatch_attempted:false` and `dispatch_outcome:not_sent`. The already consumed admission is not refunded or charged again; the same key returns the same terminal ticket after reload/restart. A provider 401/403/404/422/429 or other explicitly rejected request is terminal with `dispatch_attempted:true, dispatch_outcome:declined`. This classification relies on the GitHub API contract. A POST timeout, thrown transport exception, unexpected response or 5xx is `dispatch_uncertain`, with `dispatch_outcome:unknown`; it is reconciled by polling the original immutable request and **never retransmitted**. Arbitrary thrown transport properties cannot spoof a definite no-dispatch result.

The original source SHA and statement/action bindings remain immutable. A readiness race cannot authorize evidence from a different revision: the receipt receiver still checks the exact signed execution revision and independently checked proof receipt. The journal uses its existing states, codes, hash chain and SQLite CAS; no schema changes, production quota resets or compensating refunds were made. The new global guard uses a row in the existing rate-limit table when requests arrive.

## Atomic two-key proof admission

`admitLeanProof(env, ip, {now})` replaces the previous sequential per-client then global quota charges. One SQLite statement materializes eligibility before writing either key, then inserts/upserts both existing keys with `RETURNING`. A full client or global quota causes zero mutations: the other counter is neither created, incremented nor reset. `AS MATERIALIZED` prevents the second eligibility check from observing the first write at the final available slot. The same SHA-256/base64url keys, scopes, 2/client and 12/global limits, original first-use window behavior and strict `< cutoff` reset boundary remain unchanged. Invalid existing negative/non-integer counts fail closed. The journal CAS still permits only one admission per immutable job; the quota module has no mathematical authority.

A D1 transport failure after an atomic commit remains a possible consumed-but-unacknowledged admission; the service conservatively records failure rather than issuing a proof job or refunding uncertain work. The tests establish executed SQLite behavior, not a formal theorem about all D1 deployments.

## Remaining boundaries

Readiness can change after any GET. A workflow POST addressed to mutable `main` still relies on provider scheduling and the final signed-source receipt checks; metadata readiness is not atomic with dispatch. A process crash after a journal admission/dispatch claim remains conservative until polling or expiry; the service does not guess that a quota charge or POST never happened. Declined requests after admission are not refunded. No new real proof job, production restart/failure injection, or proof-authority claim was performed in this workstream.

Readiness GETs precede proof admission. The Worker now bounds new/created readiness attempts globally at 240 per existing 60-minute window, including exhausted proof users, in addition to the unchanged per-client 120/hour retry guard. Each newly gated attempt performs at most three metadata GETs before admission and, if admitted, three immediately before POST. Previously admitted queued requests may still complete their single final readiness check; immutable admission/dispatch claims prevent repeated checks on acknowledged or uncertain requests. Existing rate-limit windows retain their original first-use reset semantics rather than gaining a new sliding-window guarantee. The actual provider observation is specific to the tested protected revision and timestamp, not an availability guarantee for a future release.
